# Retro

Доска для ретроспектив в реальном времени: несколько человек работают с доской
одновременно, результат не зависит от порядка действий, и это проверяется машиной.
Учебный проект курса «Современные методы разработки программных продуктов с
помощью методов ИИ». Архитектура, инварианты и план работ — в
[`CLAUDE.md`](./CLAUDE.md) и
[`docs/spec/consistency-model.md`](./docs/spec/consistency-model.md).

## Запуск с нуля

Нужны Node.js 24+ (см. `.nvmrc`) и Docker.

```bash
npm install
docker compose up -d db
npm run db:migrate
npm run dev:server   # в отдельном терминале: npm run dev:web
```

Сервер поднимется на `http://localhost:3000` (`GET /healthz` → `{"status":"ok"}`),
фронтенд — на адресе, который выведет Vite (обычно `http://localhost:5173`).

Переменные окружения сервера — в `apps/server/.env.example`; скопируйте в
`apps/server/.env` при первом запуске.

## Проверки

```bash
npm run check
```

Одна команда, около двух минут. Красный прогон — работа не считается готовой (см.
`CLAUDE.md`, правило 2). Шаги по порядку:

| Шаг | Что проверяет |
|---|---|
| `check:format`, `check:lint` | форматирование и линт (Biome) |
| `check:types` | типы всех пакетов и их тестов (`tsc`) |
| `check:trace` | трассируемость: каждое REQ из `docs/spec/requirements.md` входит в задачу `docs/tasks.md`, у выполненных задач есть тесты с ID требования |
| `test:unit` | Vitest по всем workspace-пакетам, включая property-тесты fast-check в `packages/crdt` |
| `test:int` | сервер с настоящим PostgreSQL (Testcontainers, нужен Docker) |
| `test:sim` | детерминированный симулятор конкурентности (см. ниже): матрица прогонов, покрытие трудных сценариев, мутанты, регрессионные трассы |

Спецификация: `docs/brief.md` → `docs/spec/requirements.md` →
`docs/spec/consistency-model.md` и `docs/spec/protocol.md` → `docs/tasks.md`.
Симулятор описан в `docs/spec/simulator.md`.

## Симулятор конкурентности

`packages/sim` прогоняет настоящие ядра сервера и клиента (`server-core`,
`client-core`) и хранилище в памяти через детерминированную модель сети (потери,
переупорядочивание, разрывы, перезагрузки вкладок, сбои хранилища) и проверяет
свойства S1–S11: в покое все клиенты равны проекции состояния сервера, принятая
операция не теряется, отклонённая не оставляет следов, скрытые стикеры не
утекают до `reveal` и другие. Прогон целиком определяется `seed`.

```bash
npm run sim -- --clients=5 --ops=10000 --seed=42 [--profile=default]
```

Профили: `default`, `conflicts`, `chaos`, `reveal`, `votes`, `faults`. Без
`--seed` выбирается случайный и печатается первой строкой. Код выхода: 0 —
свойства выполнены, 1 — нарушено свойство (отчёт, команда повтора и трасса
`.sim/fail-<seed>.json`), 2 — неверные аргументы, несовместимая версия трассы или
внутренняя ошибка.

Разбор упавшего прогона:

```bash
npm run sim -- --replay=.sim/fail-42.json               # воспроизвести без генератора
npm run sim -- --replay=.sim/fail-42.json --minimize    # сжать до нескольких решений
```

Процедура разбора и порядок подозрений (сначала проверки и генератор самого
симулятора, потом ядра) — в скилле `.claude/skills/debug-convergence`.

Длинный набор — все профили × 5 и 20 клиентов × 20 seed по 10⁴ операций, часы:

```bash
npm run sim:long [-- --seeds=3 --concurrency=2]
```

Прогон на 20 клиентов держит около 2 ГБ памяти, поэтому параллелизм по умолчанию
считается от свободной памяти.

### Как убедиться, что симулятор проверяет что-то осмысленное

Зелёный прогон сам по себе ничего не доказывает. В проекте это проверяется отдельно:

- **Мутанты** (`packages/sim/test/mutants.test.ts`): семь намеренных поломок на
  границах ядер (пересылка очереди, `reject` → `ack`, проекция, идемпотентность и
  др.), каждая обязана быть поймана; иначе тест падает «мутант Mk выжил».
- **Покрытие трудных ситуаций** (`coverage.test.ts`, второй шаг `test:sim`): за
  набор прогонов должны случиться reveal при отключённом клиенте, конфликт текста,
  повтор `ack`, все причины отказа и т. д.; иначе — «проверка пуста: …».
- **Регрессионные трассы** (`packages/sim/test/regressions/`): минимизированные
  трассы мутантов зелёные на настоящем ядре и красные с мутантом. Пересборка:
  `npm run sim:regressions -w @retro/sim`.
- **Ручной опыт:** временно отключить досылку скрытого после `reveal` в
  `packages/server-core/src/handlers/hello.ts` (условие `guest.revealed && …`),
  пересобрать (`npx tsc -b`) и запустить профиль `default` на нескольких seed — он
  падает на S4 примерно в двух прогонах из трёх; после `git checkout` файла и
  пересборки — снова зелёный.

Граница доказательства: симулятор проверяет ядра и хранилище в памяти. Адаптер
PostgreSQL, WebSocket-слой и интерфейс он не покрывает (для них — `test:int` и
будущие e2e).

## Структура репозитория

```
apps/server/         Fastify + WebSocket + REST: тонкий адаптер над server-core и PostgreSQL
apps/web/            React SPA (пока заготовка)
packages/crdt/       ядро CRDT доски: слияние, материализация, компактизация, проводной формат
packages/protocol/   схемы протокола WS/REST (zod), общие для клиента и сервера
packages/server-core/  ядро сервера без ввода-вывода: приём операций, права, фазы, рассылка, порт хранилища
packages/client-core/  ядро клиента без браузера: подтверждённое состояние, очередь, переподключение
packages/sim/        детерминированный симулятор, мутанты, трассы, CLI (`npm run sim`)
tools/check-trace/   проверка «требование ↔ задача ↔ тест»
docs/                бриф, спецификация, ADR, проекты задач, безопасность, журнал разработки
.claude/             скиллы, агенты и хуки для агентной разработки
```

Пакеты `crdt`, `server-core`, `client-core` и `sim` чистые: без ввода-вывода,
`Date.now()` и `Math.random()`, время и случайность приходят параметрами
([ADR-0009](./docs/adr/0009-pure-cores-and-deterministic-simulator.md)). Это условие
детерминированной проверки.

## Статус

Готово: ядро CRDT, протокол, сервер (WebSocket-синхронизация, журнал операций и
снапшоты, права и фазы, голоса, видимость и `reveal`), ядра сервера и клиента,
детерминированный симулятор с мутантами и воспроизведением трасс. Впереди:
интерфейс (`apps/web`), e2e в браузерах, экспорт, проверки безопасности, деплой.
Состояние задач — `docs/tasks.md`, полный план — `CLAUDE.md` § 8.
