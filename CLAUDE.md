# Retro — доска для ретроспектив в реальном времени

Учебный проект курса «Современные методы разработки программных продуктов с помощью методов ИИ» (agentic engineering, 2026).
Задание на оценку 10: несколько человек работают с доской одновременно, **результат не зависит от порядка действий**, и это нужно **доказать машиной**, а не показать на примере.

Этот файл — одновременно правила работы для агента и план проекта. Когда разделы плана разрастутся, они уезжают в `docs/`, а здесь остаётся ссылка.

## 1. Правила работы (для агента и для человека)

1. **Спецификация раньше кода.** Любое поведение сначала описывается в `docs/spec/` требованием с ID (`REQ-XXX`) и критериями приёмки. Код без требования не пишется, требование без теста не считается выполненным.
2. **Готово = зелёный `npm run check`.** Не «я проверил», а прогон. Нельзя отмечать задачу выполненной при красных проверках.
3. **Тесты не подгоняются под код.** Запрещено ослаблять/удалять тест или property, чтобы прогон стал зелёным. Если тест неверен — сначала меняется спецификация (отдельным коммитом с объяснением), потом тест.
4. **Трассируемость.** Имя теста содержит ID требования: `it("REQ-012: concurrent moves converge", ...)`. Скрипт `npm run check:trace` падает, если у требования нет теста или тест ссылается на несуществующее требование.
5. **Решения фиксируются в ADR** (`docs/adr/NNNN-title.md`) — выбор библиотеки, протокола, семантики конфликта и т.п.
6. **Ветки и PR.** Прямые коммиты в `main` запрещены (после вехи В3). Одна задача — одна ветка `feat/REQ-XXX-short-name` — один PR с зелёной сборкой.
7. **Пакет `packages/crdt` — чистый.** Никакого I/O, `Date.now()`, `Math.random()`, зависимостей от сети/БД. Время и случайность передаются параметрами. Это условие детерминированной проверки.
8. **Никаких секретов в репозитории.** Только `.env.example`. Проверяется `gitleaks` в `check`.
9. **Журнал для отчёта.** После значимой сессии — `/journal` (хук Stop напоминает после новых коммитов), запись в `docs/report/journal.md`: что делал агент, какая модель, что пришлось доработать руками и почему, какие скиллы/MCP использовались. Из журнала собирается итоговый отчёт.
10. Код, идентификаторы, коммиты — на английском. Документация и спецификация — на русском.

## 2. Продукт

### Сценарий

Фасилитатор создаёт доску по шаблону (например, «Что было хорошо / Что улучшить / Действия»), отправляет ссылку команде. Ретро проходит по фазам:

| Фаза | Что происходит |
|---|---|
| `collect` | участники пишут стикеры; чужие стикеры скрыты до `reveal` (см. `docs/brief.md` § Анонимность) |
| `group` | стикеры видны всем, их двигают и объединяют в группы |
| `vote` | у каждого участника N голосов (N задаёт фасилитатор при создании доски), можно отдать несколько голосов одному стикеру |
| `discuss` | стикеры отсортированы по голосам, рекомендательный таймер обсуждения (не блокирует переход дальше) |
| `actions` | action items с ответственным; экспорт итогов |

### Функциональность MVP (из задания)

- стикеры: создание, редактирование текста, удаление/восстановление, цвет;
- перемещение между колонками и внутри колонки, группировка;
- голосование с лимитом голосов на участника;
- синхронизация между участниками в реальном времени, работа при временной потере сети (офлайн-очередь);
- **доказательство**: одновременные правки не теряются и приводят к одинаковому состоянию у всех.

### Вне MVP (бонусы / если останется время)

- ИИ-кластеризация стикеров и саммари ретро **с бюджетом** (лимит в день/на запрос, понятный отказ) — повод для темы harness;
- посимвольное слияние текста (RGA) вместо multi-value регистра;
- горизонтальное масштабирование сервера (Postgres `LISTEN/NOTIFY`).

### Модель данных CRDT (ядро доказательства)

Выбран **state-based (delta) CRDT**: каждая операция — это маленькое состояние-дельта, применение операции = `merge(state, delta)`. Если `merge` — объединение в полурешётке (коммутативно, ассоциативно, идемпотентно), то сходимость следует из свойств `merge`, а порядок, дубли и задержки доставки не важны. Эти три свойства и проверяются машиной.

**Точная модель, операции и инварианты — `docs/spec/consistency-model.md`.** Кратко:

- Состояние `X = (C, E, S, V⁺, V⁻)`: созданные сущности, записи в ячейки `(entity, field)`, пары перекрытия, голоса, отозванные голоса. `merge` — покомпонентное объединение.
- **Dot** `(actorId, counter)` — ID операции; actor = загрузка страницы. **Метка** `(lamport, actorId)` — общий порядок для выбора победителя. ID сущности = dot её создания.
- Запись в ячейку = новое значение + перекрытие всех значений, **видимых автору**. Видимые записи = неперекрытые. `text`/`title` показывают все видимые варианты (конфликт), остальные поля — победителя по метке. `place` = одна ячейка `(column, frac)`.
- Метаданные доски (фаза, настройки) — не CRDT, только сервер, по порядку seq.
- `materialize(X) → View` — чистая функция множества; не зависит от порядка вставки в `Map`/`Set`.
- `compact` удаляет только перекрытые записи и отозванные голоса, пары перекрытия сохраняет: `materialize(compact(X) ⊔ Y) = materialize(X ⊔ Y)`.

### Протокол синхронизации

1. Клиент подключается по WS с `boardId`, токеном сессии и `lastSeq`.
2. Сервер отвечает снапшотом или операциями с `seq > lastSeq`.
3. Клиент применяет операцию локально (оптимистично), кладёт в outbox, отправляет `{type: "op", dot, lamport, delta}`.
4. Сервер: валидирует схему → **перезаписывает `actorId` из сессии** (клиенту не доверяем) → проверяет права, фазу, лимит голосов, границы Lamport → `INSERT ... ON CONFLICT (board_id, actor, counter) DO NOTHING` → присваивает `seq` → `ack` автору, `broadcast` остальным.
5. Отклонённая операция → `reject {dot, reason}`. Клиент хранит подтверждённое состояние и очередь ожидающих дельт отдельно, поэтому просто удаляет дельту из очереди и пересчитывает экран, как будто её не было. Компенсирующих операций нет. Причина показывается пользователю.
6. При переподключении outbox отправляется заново; дубли гасятся уникальным индексом (идемпотентность).

Намеренные асимметрии, которые спецификация должна описать явно:
- фаза `collect` со скрытыми стикерами — чужой текст не отправляется до `reveal`; сходимость формулируется «у участников с одинаковой видимостью» и «у всех после reveal».

**Решение по брифу (docs/brief.md):** анонимность в MVP — только временная, на время `collect`, до `reveal`. Отдельного постоянного «анонимного режима», где автор не раскрывается никогда и никому, в MVP нет (упрощает протокол и модель угроз). `authorId` хранится вне CRDT и не рассылается только пока стикер скрыт; после `reveal` он виден всем как обычно.

## 4. Как доказывается правильность (задание на 10)

| Что доказываем | Как | Где |
|---|---|---|
| `merge` — полурешётка | fast-check: коммутативность, ассоциативность, идемпотентность на сгенерированных состояниях | `packages/crdt/test/lattice.prop.test.ts` |
| Сходимость | N реплик получают одно множество операций в случайных перестановках, с дублями и задержками → `materialize` побайтно равен | `packages/crdt/test/convergence.prop.test.ts` |
| Правки не теряются | для каждой сгенерированной операции её dot присутствует в итоговом состоянии; каждая конкурентная запись `text` видна либо как значение, либо как конфликт | `packages/crdt/test/no-loss.prop.test.ts` |
| Независимость от порядка вставки | `materialize` на состояниях, собранных в разном порядке, совпадает | `packages/crdt/test/materialize.prop.test.ts` |
| Компактизация безопасна | `materialize(compact(X) ⊔ Y) == materialize(X ⊔ Y)` для любых X, Y | `packages/crdt/test/compact.prop.test.ts` |
| Система целиком | симулятор: 2–20 клиентов, реальный `BoardHub`, сеть с потерями/переупорядочиванием/разрывами, 10⁴ операций → все клиенты и БД сходятся | `packages/sim` |
| Журнал ↔ снапшот | replay операций из Postgres равен снапшоту | `apps/server/test/oplog.int.test.ts` |
| Реальный браузер | Playwright: 3 контекста, одновременное перемещение/редактирование одного стикера, один офлайн → после сети состояние DOM одинаково | `e2e/concurrency.spec.ts` |
| Тесты действительно ловят баги | мутационное тестирование `packages/crdt` (Stryker), порог mutation score ≥ 80% | `npm run check:mutation` (nightly) |

Упавший property-тест печатает `seed` и минимизированный контрпример; контрпример добавляется в regression-тесты.

## 5. Границы: права, угрозы, цена

### Матрица прав (черновик, источник истины — `docs/security/permissions.md`)

| Действие | owner | facilitator | participant | viewer |
|---|:-:|:-:|:-:|:-:|
| создать/редактировать свой стикер | ✅ | ✅ | ✅ (фазы collect/group) | ❌ |
| редактировать чужой стикер | ✅ | ✅ | ❌ | ❌ |
| перемещать/группировать | ✅ | ✅ | ✅ (group) | ❌ |
| голосовать | ✅ | ✅ | ✅ (vote, ≤ N) | ❌ |
| сменить фазу, reveal | ✅ | ✅ | ❌ | ❌ |
| **сбросить голоса** ⚠️ | ✅ | ✅ | ❌ | ❌ |
| **раскрыть автора скрытого стикера до `reveal`** ⚠️ | ❌ (запрещено всем, включая владельца) | ❌ | ❌ | ❌ |
| **удалить доску** ⚠️ | ✅ + подтверждение, soft delete 7 дней | ❌ | ❌ | ❌ |
| экспорт | ✅ | ✅ | ✅ | ✅ |

`tools/check-perms` парсит матрицу и сверяет с таблицей `permissions` в коде обработчиков; тест пытается выполнить каждое запрещённое действие каждой ролью и **конвейер падает, если хоть одно прошло** (веха В5).

### Модель угроз (ключевые векторы — проверить на своём проекте)

- **Подмена actorId** в операции → сервер берёт актора только из сессии.
- **Инфляция Lamport-часов** (клиент шлёт `clock = 2^53`, после чего его запись навсегда побеждает) → сервер отклоняет `lamport > serverClock + K`.
- **Раздувание состояния**: огромный текст, миллионы `supersedes`, флуд операций → лимиты размера сообщения и дельты, rate limit на актора и на доску, лимит стикеров на доску.
- **XSS через текст стикера** и через SSR-страницу итогов → только текстовый рендер, CSP, тест с подложенным payload.
- **Cross-Site WebSocket Hijacking** → проверка `Origin`, cookie `SameSite=Strict`.
- **Перебор ссылок на доски** → неугадываемые ID (128 бит), rate limit на join.
- **Утечка авторства до `reveal`** через порядок/время операций в broadcast → `authorId` не рассылается, пока стикер скрыт; временные метки на этот период огрубляются.
- **Prompt injection** в стикерах (если делаем ИИ-саммари) → текст стикеров передаётся как данные, у модели нет инструментов с побочными эффектами.

Своя проверка безопасности (бонус): `npm run check:security` — semgrep-правила + тесты-атаки из списка выше; в `security/planted/` лежит ветка с подложенной уязвимостью (например, актор берётся из сообщения), и CI доказывает, что проверка на ней падает.

### Цена и лимиты

- Сервер: лимиты подключений на доску (50), операций в секунду на актора (20), размер сообщения (16 KB).
- Агентная разработка: бюджет на модели фиксируется в `docs/report/journal.md` (модель, задача, примерная стоимость).
- ИИ-функции (если будут): лимит в день и на запрос в таблице `usage`, при исчерпании — понятный отказ, а не превышение.

2. `check:types` — `tsc -b`

## 7. Агентная обвязка: скиллы, агенты, MCP

### Принцип разделения

- **Скилл** — повторяемая процедура или знание о проекте; подгружается в главную сессию.
- **Агент** — отдельный контекст, своя модель, урезанные инструменты. Только там, где нужна **независимость** («проверяет не тот, кто делал»).
- **Хук** — правило, которое должно выполняться всегда, а не «когда модель вспомнит». Ограничения агентов на пути и команды — хуками, не текстом инструкции.

### Скиллы (`.claude/skills/`)

**Известное ограничение (проверено на В2 и В3):** используемый харнесс не индексирует `.claude/skills/*` и `.claude/agents/*` этой сессии как вызываемые по имени (`Skill`/`Agent` возвращают «Unknown skill»/запускают дженерик-агента вместо именованного типа). Все скиллы выше реально выполнялись — но вручную, по тексту `SKILL.md`, а не через вызов по имени. Для агентов это существеннее: `test-author` запускался как `general-purpose` с его инструкцией в промпте, из-за чего **хуки из frontmatter агента не срабатывали** — ограничения на пути соблюдались по инструкции, а не принудительно. Дальше в цикле разработки поведение так и остаётся: агент читает не то, что hard-запрещено хуком, а то, что попросили в промпте не читать. При работе в среде, которая подхватывает `.claude/agents`, это ограничение снимается само.

### Хуки (`.claude/settings.json`, `.claude/hooks/`)

| Хук | Событие | Что делает |
|---|---|---|
| `guard-bash.mjs` | PreToolUse Bash | запрет force push; git-запись только если корень git = корень проекта; при наличии `.claude/protect-main` (включить на В3) — запрет коммитов и push в `main`; `--readonly` для проверяющего |
| `guard-paths.mjs` | PreToolUse файловых инструментов агентов | `--allow`/`--deny` по glob относительно корня проекта |

Известные ограничения: Grep/Glob без явного `path` хук путей не проверяет; `--readonly` для Bash — эвристика по регуляркам, а не песочница. На вехе В2 проверить, что хуки из frontmatter агентов действительно срабатывают (попросить `test-author` записать файл в `apps/`).

### Модели

Главная сессия и реализация — Opus 5; `test-author` и `spec-reviewer` — Sonnet 5 (другая модель, чем у автора кода: меньше общих слепых пятен и дешевле); механические скиллы (`milestone-check`, `journal`) — Haiku 4.5. Фактическое использование фиксируется в журнале.

### MCP-серверы

- **Playwright MCP** — агент открывает доску в нескольких вкладках и проверяет синхронизацию глазами.
- **Postgres MCP** (read-only пользователь БД) — просмотр журнала операций при отладке.
- **GitHub MCP / `gh`** — ветки, PR, статус CI.
- **Свой `tools/retro-mcp`** (бонус): инструменты `simulate(clients, ops, seed)`, `replay_board(boardId)`, `diff_replicas(seed)`, `explain_conflict(stickerId)` — агент исследует конкурентные баги не читая код.

### Цикл без человека (бонус, тема 14)

`.github/workflows/agent-loop.yml` по расписанию: берёт issue с меткой `agent-ok` → ветка → реализация через `implement-req` → PR. Границы: не трогает `packages/crdt/test/**`, `docs/spec/**`, `docs/security/**`, workflow-файлы; не мёржит сам; ≤ 1 PR в день; лимит токенов на запуск; при красном `check` после 2 попыток закрывает PR с отчётом. Нарушение границ проверяется отдельным job по diff.
