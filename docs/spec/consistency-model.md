# Модель согласованности доски и инварианты

- **Статус:** черновик, 2026-09-13
- **Назначение:** источник истины для `packages/crdt`, протокола синхронизации и property-тестов. Изменения — только через ADR.
- **Как читать:** каждое формальное утверждение сопровождается пояснением «по-русски». Доказательства — эскизы в §9, проверка машиной — §11.

---

## 0. Словарь в одну строку

| Термин | Что это |
|---|---|
| **реплика** | одна копия доски: вкладка браузера у участника или сервер |
| **dot** | уникальный идентификатор операции: «кто (актор) и какая по счёту» |
| **метка (stamp)** | логическое время Lamport + актор; задаёт один общий порядок всех операций |
| **состояние X** | пять множеств, в которые только добавляют (§2) |
| **дельта δ** | маленькое состояние, которое производит одна операция |
| **merge (⊔)** | слияние двух состояний — объединение множеств покомпонентно |
| **materialize** | чистая функция «состояние → то, что видно на экране» (§4) |
| **проекция proj_u** | часть состояния, которую участнику u разрешено видеть (§5) |
| **журнал (Log)** | последовательность принятых сервером дельт с номерами seq (§6) |
| **replay** | слить все дельты журнала по порядку, начиная с пустого состояния |
| **compact** | выбросить из состояния записи, которые уже никогда не будут видны (§6) |
| **snapshot** | сохранённый результат `compact(replay(первые m дельт))` вместе с номером m |

## 0.1 Обозначения

| Знак | Смысл |
|---|---|
| `A × B` | пары (a, b) |
| `P(A)` | конечные подмножества A |
| `⊥` | пустое состояние |
| `X ⊔ Y` | слияние состояний |
| `X ⊑ Y` | X содержится в Y покомпонентно |
| `argmax_{e ∈ M} e.t` | элемент M с наибольшей меткой |
| `\|M\|` | число элементов |

## 1. Базовые понятия

### 1.1 Акторы и пользователи

`U` — пользователи, `A` — акторы. **Актор — одна загрузка страницы** (или один процесс сервера), `actorId` — случайные 128 бит, генерируется при загрузке. Сервер знает `owner: A → U`.

> По-русски: у одного человека в двух вкладках — два актора. Счётчик операций не нужно хранить между перезагрузками, поэтому dot никогда не повторится.

### 1.2 Dot

```text
Dot = A × ℕ⁺
```

Актор хранит счётчик `n`; каждая операция берёт следующее значение. На `Dot` задан полный порядок: лексикографически по байтам `a`, затем по `n`. Он нужен только для однозначной сортировки при равенстве остального.

> По-русски: dot `(ab12…, 7)` — «седьмая операция вкладки ab12…». Двух операций с одинаковым dot не бывает.

### 1.3 Метка Lamport

```text
Stamp = ℕ × A                    порядок: сначала по числу, затем по актору
```

Акторы сравниваются как строки по кодовым единицам UTF-16 (оператор `<` в JavaScript); для `actorId` в виде UUID это совпадает с побайтовым сравнением из § 1.2.

Каждая реплика хранит число `L`:

- получила состояние `Y` → `L := max(L, max{ t.L | метка t встречается в Y })`;
- выполняет свою операцию → `L := L + 1`, метка операции `t := (L, a)`.

**Свойства.** (а) Метки разных операций различны. (б) Если реплика создала операцию `o₂`, уже имея в состоянии операцию `o₁`, то `t(o₁) < t(o₂)`.

> По-русски: метка — «логическое время». Всё, что ты видел, заведомо «раньше» того, что ты делаешь. У одновременных операций порядок произвольный, но одинаковый у всех.

### 1.4 Сущности и поля

```text
Kind     = { sticker, group, action }
EntityId = Dot                    — id сущности = dot операции её создания
Key      = EntityId × Field       — «ячейка»: конкретное поле конкретной сущности
Col      — фиксированное множество колонок шаблона доски
Frac     — дробные индексы (строки), порядок лексикографический
```

| Kind | Field | Значения | Политика разрешения |
|---|---|---|---|
| sticker | `text` | строка ≤ 2000 символов | **все** видимые варианты (конфликт) |
| sticker | `color` | палитра | победитель по метке |
| sticker | `place` | `Col × Frac` | победитель по метке |
| sticker | `group` | `GroupId ∪ {none}` | победитель по метке |
| sticker | `deleted` | `Bool` | победитель по метке |
| group | `title` | строка ≤ 200 | **все** видимые варианты |
| group | `place`, `deleted` | как у стикера | победитель по метке |
| action | `text` | строка ≤ 2000 | **все** видимые варианты |
| action | `assignee` | `U ∪ {none}` | победитель по метке |
| action | `done`, `deleted` | `Bool` | победитель по метке |

`place` — одно поле-пара, а не две ячейки «колонка» и «позиция»: иначе при одновременных перемещениях колонка взялась бы от одного, а позиция от другого.

## 2. Состояние и слияние

```text
X = (C, E, S, V⁺, V⁻)

C  ⊆ EntityId × Kind                  созданные сущности
E  ⊆ Key × Dot × Stamp × Value        записи в ячейки: e = (k, d, t, v)
S  ⊆ Key × Dot                        перекрытия: «запись d в ячейке k перекрыта»
V⁺ ⊆ Dot × U × EntityId               голоса: (dot, кто, за что)
V⁻ ⊆ Dot × EntityId                   отозванные голоса: (dot голоса, за что)

⊥      = (∅, ∅, ∅, ∅, ∅)
X ⊑ Y  ⇔  каждая компонента X ⊆ соответствующей компоненты Y
X ⊔ Y  =  (C_X ∪ C_Y, E_X ∪ E_Y, S_X ∪ S_Y, V⁺_X ∪ V⁺_Y, V⁻_X ∪ V⁻_Y)
```

> По-русски: состояние — пять мешков. Операции только **кладут** в них. Слить две реплики — высыпать мешки в общий. Ничего никогда не вынимается (кроме компактизации, §6, которая вынимает только то, что и так никогда не будет видно).

### Производные функции

```text
vis_k(X)   = { e ∈ E | e.k = k ∧ (k, e.d) ∉ S }            видимые записи ячейки
win_k(X)   = argmax_{e ∈ vis_k(X)} e.t                     победитель (единственный: метки различны)
vals_k(X)  = [ e.v | e ∈ vis_k(X) ], по убыванию e.t       все видимые значения
exists(id) = ∃ kind: (id, kind) ∈ C
deleted(id)= win_(id, deleted)(X).v
active(X)  = { v ∈ V⁺ | (v.d, v.target) ∉ V⁻ }             действующие голоса
```

> По-русски: в ячейке может лежать несколько записей. Видимы те, которые никто не перекрыл. Если видимая одна — это значение. Если несколько — это одновременные правки: у текста показываем все, у остальных полей берём самую «позднюю» по метке.

## 3. Операции

Операция выполняется на реплике с текущим состоянием `X` (для клиента — то, что он видит: подтверждённое + ожидающее, §6). Она берёт свежие `d` и `t` (§1.2–1.3), строит дельту `δ` и применяет `X := X ⊔ δ`.

Вспомогательное:

```text
sup(k, X)   = { (k, e.d) | e ∈ vis_k(X) }        «всё, что я сейчас вижу в этой ячейке»
write(k, v) = ( ∅, {(k, d, t, v)}, sup(k, X), ∅, ∅ )
```

> По-русски: запись в ячейку = новое значение + пометка «я видел вот эти значения и заменяю их». Значения, которых автор не видел, не перекрываются — поэтому одновременные правки остаются.

### 3.1 Операции над доской (CRDT)

| Операция | Дельта |
|---|---|
| `createSticker(col, frac, text, color)` | `C = {(d, sticker)}`; `E = {((d,text),d,t,text), ((d,color),d,t,color), ((d,place),d,t,(col,frac)), ((d,group),d,t,none), ((d,deleted),d,t,false)}`; `S = ∅` |
| `editText(id, text)` | `write((id, text), text)` |
| `resolveText(id, text)` | то же, что `editText`: `sup` перекрывает **все** видимые варианты, конфликт исчезает |
| `setColor(id, c)` | `write((id, color), c)` |
| `move(id, col, frac)` | `write((id, place), (col, frac))` |
| `setGroup(id, g)` | `write((id, group), g)`, `g ∈ GroupId ∪ {none}` |
| `delete(id)` / `restore(id)` | `write((id, deleted), true / false)` |
| `createGroup(col, frac, title)` | `C = {(d, group)}`; записи `title`, `place`, `deleted=false` с dot `d` |
| `renameGroup`, `moveGroup`, `deleteGroup`, `restoreGroup` | `write` в соответствующую ячейку |
| `createAction(text)` | `C = {(d, action)}`; записи `text`, `assignee=none`, `done=false`, `deleted=false` |
| `editAction`, `assign`, `setDone`, `deleteAction` | `write` в соответствующую ячейку |
| `vote(id)` | `V⁺ = {(d, owner(a), id)}` |
| `unvote(vd, id)` | `V⁻ = {(vd, id)}` |

Все записи одной операции несут один и тот же dot `d` (в разных ячейках).

### 3.2 Операции над метаданными (не CRDT)

`setPhase`, `reveal`, `setSettings`, `deleteBoard` меняют метаданные доски `M`. Их выполняет только сервер, строго по порядку seq. В `X` они не входят и слиянием не обрабатываются.

**Ограничение Р1.** Переходы `M` только **расширяют** видимость: то, что участник однажды увидел, не скрывается снова.

## 4. Материализация

```text
materialize : X → View
```

**Ограничение M1.** `materialize(X)` зависит от `X` **только** через `C`, функции `vis_k` и `active(X)`.

```text
View      = ( columns: Col → List<Item>, trash: List<EntityId>, actions: List<ActionView> )
Item      = CardView | GroupView
CardView  = ( id, text: List<String>, conflict: Bool, color, votes: ℕ )
GroupView = ( id, title: List<String>, conflict: Bool, cards: List<CardView>, votes: ℕ )
```

Правила:

- **R1.** Сущность показывается, если `exists(id) ∧ ¬deleted(id)`. Существующая удалённая — в `trash`. Записи ячеек без записи в `C` игнорируются (операция создания ещё не пришла).
- **R2.** `text = vals_(id,text)`, `conflict = |text| > 1`; для `title` так же. `color = win_(id,color).v`.
- **R3.** Эффективная группа стикера `g* = win_(id,group).v`, если `g* ≠ none ∧ exists(g*) ∧ kind(g*) = group ∧ ¬deleted(g*)`, иначе `none`.
- **R4.** Стикер с `g* = none` лежит в колонке `win_(id,place).v.col`; с `g* ≠ none` — внутри группы, его собственный `place` не используется.
- **R5.** Порядок внутри колонки и группы: по `(frac, id)` по возрастанию. При равных `frac` решает порядок `Dot`.
- **R6.** `votes(id) = |{ v ∈ active(X) | v.target = id }|`. Голоса за удалённый стикер не показываются, но остаются в `active`.
- **R7.** `trash` и `actions` отсортированы по `id`.

Все используемые порядки полные и зависят только от значений, поэтому `materialize` — корректно определённая функция **множества** `X`, а не того, в каком порядке его собирали.

## 5. Проекция видимости

`visible(u, id, M)` — предикат из метаданных и автора сущности (автор хранится на сервере вне `X`). Например, в фазе `collect` со скрытием: `visible ⇔ author(id) = u`; в остальных фазах — всегда `true`.

```text
proj_u(X) = ( {c ∈ C | visible(u, c.id)},
              {e ∈ E | visible(u, e.k.id)},
              {s ∈ S | visible(u, s.k.id)},
              {v ∈ V⁺ | visible(u, v.target)},
              {w ∈ V⁻ | visible(u, w.target)} )
```

- **P1.** `proj_u(X ⊔ Y) = proj_u(X) ⊔ proj_u(Y)` — проекция фильтрует каждый элемент независимо от остальных.
- **P2.** При смене `M` по Р1 новая проекция содержит старую: `proj_u ⊑ proj'_u`.

> По-русски: во время сбора мнений участник видит только свои стикеры. Проекция — фильтр, поэтому «отфильтровать, потом слить» и «слить, потом отфильтровать» дают одно и то же.

## 6. Реплики, журнал, снапшот, компактизация

### Сервер

```text
Log         = [ (1, δ₁), (2, δ₂), … ]          принятые дельты
X_S(n)      = replay(Log[1..n]) = ⊥ ⊔ δ₁ ⊔ … ⊔ δₙ
compact(X)  = ( C, {e ∈ E | (e.k, e.d) ∉ S}, S, {v ∈ V⁺ | (v.d, v.target) ∉ V⁻}, V⁻ )
snapshot(m) = ( m, compact(X_S(m)) )
восстановление: X_S(n) ≈ compact(X_S(m)) ⊔ δ_{m+1} ⊔ … ⊔ δₙ     (≈ — равны после materialize, I5)
```

> По-русски: компактизация выбрасывает только перекрытые записи и отозванные голоса. Пометки о перекрытии (`S`, `V⁻` — это пары «ячейка + dot», они маленькие) остаются, поэтому поздно пришедшая старая запись всё равно останется невидимой.

### Клиент u

```text
X_c(u)  — подтверждённое: ⊔ proj_u(snapshot) и всех полученных proj_u(δᵢ)
P(u)    — список своих дельт, отправленных, но ещё не подтверждённых
D(u)    = materialize( X_c(u) ⊔ ⨆P(u) )          то, что на экране
```

- `ack(δ)`: δ переносится из `P` в `X_c`.
- `reject(δ)`: δ удаляется из `P`. Экран пересчитывается, **как будто δ не было**. Компенсирующих операций нет.
- **Покой** клиента u в момент n: `P(u) = ∅` и u получил `proj_u(δᵢ)` для всех `i ≤ n`.

## 7. Правила приёма операции сервером

Дельта `δ` от актора `a` пользователя `u` принимается, только если выполнены все правила. Сервер обрабатывает дельты одной доски **последовательно**.

| # | Правило |
|---|---|
| V1 | **Свежий dot.** Применяется к `create`/`write`/`vote` — операциям с собственным dot операции `(a, n)`: `owner(a) = u`; `n > last_n(a)`. Если `(a, n)` уже в журнале — это повтор: `ack` без применения. Если `n ≤ last_n(a)` и в журнале нет — отказ. **Не применяется к `unvote(vd, id)`**: `vd` — dot **чужой, более ранней** операции `vote` (§ 3.1), не собственный dot операции отзыва — актор `vd` в общем случае не совпадает с актором соединения, отправившего `unvote` (другая вкладка того же `guestId`, или та же вкладка после перезагрузки, REQ-002 кр. 2). Принадлежность `vd` пользователю `u` и его действительность — V7, не V1 (ADR-0008). |
| V2 | **Форма.** δ — ровно одна операция из §3.1; значения из своих доменов; `place.col ∈ Col`; лимиты размера. |
| V3 | **Цель существует.** Для `write`, `vote`, `unvote` сущность `id ∈ C(X_S)` нужного вида; для `setGroup` — `g = none` или группа из `C(X_S)`. |
| V4 | **Перекрытие обосновано.** Все пары `(k, s) ∈ δ.S` относятся к ячейке записи δ, и для каждой есть запись `e ∈ E(X_S)` с `e.k = k, e.d = s, e.t < δ.t` (или пара уже в `S(X_S)`). |
| V5 | **Метка.** `t.a = a`; `t.L > last_L(a)`; `t.L ≤ L_S + K`, где `L_S` — максимум по `X_S`, `K` ≥ максимального размера очереди клиента. |
| V6 | **Права и фаза** — по `docs/security/permissions.md`. |
| V7 | **Голоса.** `vote`: у u сейчас `< N` действующих голосов. `unvote(vd, id)`: если `(vd, id)` уже в `V⁻` журнала (кем угодно — тем же клиентом повторно, `resetVotes` от лица сервера) — повтор: `ack` без применения (2P-set идемпотентен по построению, ADR-0008), не относится к V1 (нет собственного dot операции у `unvote`). Иначе — голос `vd` должен существовать и принадлежать u; иначе отказ (`not_own_vote`). |

### Инварианты корректной формы (держатся по индукции по журналу)

- **W1.** В одной ячейке не больше одной записи с данным dot; разные операции имеют разные dot. *(V1)*
- **W2.** Разные операции имеют разные метки. *(V5)*
- **W3.** Каждая пара `(k, s) ∈ S` пришла в одной дельте с записью `e'` в ячейке k, и `e'.t` больше метки записи `s`. *(V4, дельта применяется целиком)*
- **W4.** Для каждой `(id, kind) ∈ C` в журнале есть записи с dot `id` во **всех** полях этого вида. *(V2: форма операций создания)*

## 8. Инварианты

### I1. Сходимость

**I1.1 — порядок доставки не важен (уровень `packages/crdt`).**

```text
∀ конечных последовательностей дельт s, s' :  set(s) = set(s')
    ⇒  fold(⊔, ⊥, s) = fold(⊔, ⊥, s')  =  ⨆ set(s)
```

> По-русски: если две реплики получили одни и те же операции — в любом порядке, с повторами, пачками или по одной — их состояния совпадают буквально.

**I1.2 — система в покое.**

```text
∀ n, ∀ клиента u в покое в момент n :   X_c(u) = proj_u( X_S(n) )
```

**Следствие.** Два клиента `u, w` в покое с одинаковой видимостью (`proj_u = proj_w`) видят одинаковый экран: `D(u) = D(w) = materialize(proj_u(X_S(n)))`. После `reveal` видимость у всех одинакова, значит, одинаковый экран у всех.

> По-русски: когда сеть «успокоилась», каждый участник видит ровно то, что лежит на сервере, за вычетом того, что ему пока не положено видеть.

### I2. Ничто не пропадает молча

**I2.1 — записи.**

```text
∀ принятой δ, ∀ e ∈ δ.E, ∀ n после её принятия:
    e ∈ vis(X_S(n))
  ∨ ∃ принятая δ' : (e.k, e.d) ∈ δ'.S      — и тогда δ'.t > e.t, а автор δ' видел e (V4, свойство 1.3б)
```

> По-русски: запись может стать невидимой только одним способом — кто-то, **у кого она была на экране**, сознательно её заменил. Одновременная правка, которую автор не видел, не перекрывает.

**I2.2 — текст.** Для полей с политикой «все варианты» на экране показываются значения **всех** неперекрытых записей: `text = vals_k`. Одновременные правки текста всегда видны как конфликт.

**I2.3 — поля-победители.** Неперекрытые проигравшие записи (`place`, `color`, `group`, …) остаются в `E` — в том числе после компактизации — и доступны истории.

**I2.4 — сущности.** `∀ (id, kind) ∈ C`: `id` находится либо в `columns`/`actions` (возможно, внутри группы), либо в `trash`.

**I2.5 — голоса.** `∀ v ∈ V⁺`: `v ∈ active`, либо сам владелец отозвал его через `unvote` (V7).

**I2.6 — нет пустых ячеек.** `exists(id) ⇒ vis_(id,f) ≠ ∅` для каждого поля `f` вида сущности.

### I3. Детерминизм материализации

```text
∀ X :  materialize(X) не зависит от порядка, в котором элементы добавлялись в структуры данных реализации
```

> По-русски: математически это следует из §4. Для кода это обязательство: никакого обхода `Map`/`Set` без сортировки.

### I4. Безопасность компактизации

```text
∀ достижимого X, ∀ Y :   materialize( compact(X) ⊔ Y ) = materialize( X ⊔ Y )
```

> По-русски: после сжатия состояния можно продолжать сливать с чем угодно — в том числе с устаревшими репликами — и экран будет тем же, как если бы сжатия не было.

### I5. Журнал и снапшот согласованы

```text
∀ m ≤ n :   materialize( compact(X_S(m)) ⊔ δ_{m+1} ⊔ … ⊔ δₙ ) = materialize( X_S(n) )
```

### I6. Лимит голосов

```text
∀ n, ∀ u :   |{ v ∈ active(X_S(n)) | v.user = u }| ≤ N
```

Голоса за удалённые стикеры тоже считаются в лимит (иначе «удалить → проголосовать → восстановить» превышало бы лимит). *Открытый вопрос спецификации.*

## 9. Доказательства (эскизы)

**Т1 (решётка) ⇒ I1.1.**
Компоненты `X` — конечные множества, `⊔` — объединение. Объединение коммутативно, ассоциативно и идемпотентно. Индукцией по длине: `fold(s·x) = fold(s) ⊔ x`, поэтому `fold(s) = ⨆ set(s)`. Перестановки поглощаются коммутативностью и ассоциативностью, повторы — идемпотентностью. ∎

**Т2 ⇒ I1.2.**
Сервер отправляет u `proj_u` каждой принятой δᵢ (или снапшот + хвост). Своя δ после `ack` — это одна из δᵢ, отклонённая не попадает ни в журнал, ни в `X_c`. По Т1 и P1: `X_c(u) = ⨆ proj_u(δᵢ) = proj_u(⨆ δᵢ)`. В покое получены все `i ≤ n`, значит `X_c(u) = proj_u(X_S(n))`. При расширении видимости (P2) сервер досылает недостающее, и равенство восстанавливается с новой проекцией. ∎

**Т3 ⇒ I2.1, I2.3, I2.5.**
Без компактизации `E` только растёт, значит, e остаётся в `E`. Невидима ⇔ `(k, e.d) ∈ S`. `S` пополняется только дельтами, значит, пару принесла некоторая принятая δ'; по V4 `δ'.t > e.t`, и e была в состоянии автора. Компактизация убирает только записи с парой в `S`, поэтому неперекрытые проигравшие остаются. Для голосов: `V⁻` пополняется только через `unvote`, а V7 разрешает его только владельцу. ∎

**Т4 ⇒ I2.6.**
По W4 в ячейке `(id, f)` есть хотя бы одна запись. Возьмём запись `e*` с максимальной меткой среди всех, когда-либо принятых в эту ячейку. Если бы `(k, e*.d) ∈ S`, то по W3 существовала бы запись в той же ячейке с большей меткой — противоречие. Значит, `e*` не перекрыта, компактизацией не удаляется и лежит в `vis`. ∎

**Т5 ⇒ I4.**
`compact` удаляет из `E` только записи с `(k, d) ∈ S_X ⊆ S_{X⊔Y}` — они и так невидимы в `X ⊔ Y`. Если такая запись снова придёт в `Y`, пара в `S` сохранена, и она снова невидима. `C`, `S`, `V⁻` не меняются. Значит, для всех k `vis_k(compact(X) ⊔ Y) = vis_k(X ⊔ Y)`, и `active` совпадают. По M1 совпадает и `materialize`. ∎

**Т6 ⇒ I5.**
`X_S(m) ⊔ δ_{m+1} ⊔ … ⊔ δₙ = X_S(n)` по Т1. Применяем Т5 с `X = X_S(m)`, `Y = δ_{m+1} ⊔ … ⊔ δₙ`. ∎

**Т7 ⇒ I6.**
Индукция по журналу. Изначально голосов нет. `vote` принимается только при числе голосов `< N` (V7) — после него `≤ N`. `unvote` число уменьшает. Остальные операции `active` не меняют. Существенно, что дельты одной доски обрабатываются последовательно. ∎

**Предположения, на которых всё держится:**
- сервер обрабатывает дельты одной доски последовательно (для нескольких экземпляров сервера нужен ADR);
- канал клиент → сервер сохраняет порядок (WebSocket; при переподключении очередь отправляется в исходном порядке);
- реализация `⊔`, `compact`, `materialize` совпадает с определениями выше — именно это проверяется тестами.

## 10. Чего модель не гарантирует

- При одновременных перемещениях на экране одно; другое хранится, но не показывается (I2.3).
- Текст сливается целиком, а не посимвольно: две одновременные правки — два варианта и конфликт.
- Стикеры с одинаковым `frac` упорядочены по dot — стабильно, но не «по намерению».
- Клиенты **не в покое** могут временно видеть разное.
- Задержка доставки — отдельные нефункциональные требования, не часть этой модели.
