# ADR-0007: Отдельная ссылка-приглашение на каждую роль (participant / viewer)

- **Статус:** принято
- **Дата:** 2026-09-14

## Контекст

T-007 («Создание доски, гостевая сессия, роли») требует решить то, что `docs/spec/requirements.md` явно не решает: REQ-001 описывает, что создатель доски становится `owner`+`facilitator`, REQ-003 — что `owner` может назначить `facilitator`, но ни один REQ не говорит, какую роль (`participant` или `viewer`) получает новый гость, впервые открывший ссылку на доску. `docs/brief.md` § Для кого перечисляет обе роли («наблюдатель — например, менеджер, которого пригласили посмотреть»), подразумевая, что это разные приглашения, а не одна ссылка с последующим ручным понижением.

## Решение

Одна доска — две отдельные, независимо неугадываемые ссылки-приглашения: одна выдаёт роль `participant`, другая — `viewer`. Роль гостя определяется тем, по какой из двух ссылок он впервые присоединился, и затем фиксируется в `members` — как обычная гостевая сессия (REQ-002, sticky: роль не пересчитывается при каждом заходе, а хранится один раз).

### Механика

- `boards` получает `owner_id` (guestId создателя). Создатель добавляется в `members` с ролью `owner` синхронно при `POST /api/boards`, ссылка ему не нужна — доступ по `boardId` напрямую (проверка `guestId === boards.owner_id`).
- Две новые непрозрачные 128-битные строки на доску — `participantLinkToken`, `viewerLinkToken` (тот же уровень неугадываемости, что и `boardId`, `CLAUDE.md` § 5 модель угроз). Хранятся в `boards` (2 колонки) или отдельной таблице — деталь реализации T-007, не протокола.
- `POST /api/boards` (REQ-001) возвращает `{ boardId, participantLink, viewerLink }` вместо только `{ boardId }`.
- Новый REST-эндпоинт `GET /api/boards/join/:token` (`docs/spec/protocol.md` § 7): резолвит токен → `(boardId, role)`; если у `guestId` из `X-Guest-Id` ещё нет записи в `members` этой доски — создаёт её с этой ролью; если уже есть — возвращает **существующую** роль, токен не меняет её задним числом (REQ-002 кр.2, sticky). Ссылка не одноразовая: два разных гостя по одной ссылке получают одну и ту же роль.
- `GET /api/boards/:boardId` (уже существующий в протоколе) доступен только тем, кто уже есть в `members` (или совпадает `owner_id`) — не создаёт членство сам, в отличие от `join`. Не член — `404`, а не `403` (не подтверждаем существование доски посторонним).

## Рассмотренные варианты

- **Две отдельные ссылки на роль (выбран)** — соответствует уже написанному тексту брифа («пригласили посмотреть»); не меняет модель данных `members` (по-прежнему одна роль на гостя), не требует ручного действия `owner`/`facilitator` для каждого наблюдателя.
- **Одна ссылка, роль по умолчанию `participant`, `viewer` — только ручное понижение** — отклонено пользователем: не соответствует сценарию «пригласили только посмотреть» без дополнительного шага модерации; было бы проще для T-007, но продуктово хуже.

## Последствия

- `docs/spec/requirements.md`: REQ-001 (критерий про содержимое ответа создания), REQ-002 (новые критерии про роль по ссылке) — дополнены.
- `docs/spec/protocol.md` § 2 (новый идентификатор `linkToken`), § 7 (новый эндпоинт `join`, изменён ответ `POST /api/boards`).
- `apps/server`: миграция добавляет `owner_id` в `boards`, создаёт `members`; линк-токены — либо колонки `boards`, либо отдельная таблица (решает T-007 по месту).
- Если позже понадобится приглашать конкретного человека (именная ссылка, не общая на роль) — отдельный ADR, эта схема не выбрасывается, становится ролью по умолчанию для «общей» ссылки.
