# ADR-0005: Журнал операций в PostgreSQL + периодические снапшоты

- **Статус:** принято
- **Дата:** 2026-09-13

## Контекст

Состояние доски должно переживать перезапуск сервера (REQ-027) и позволять клиенту переподключиться, получив только то, что он ещё не видел (REQ-023). Хранить только «последнее состояние» без истории операций не даёт воспроизвести дельты для клиента, который отстал на несколько операций, — пришлось бы каждый раз слать полный снапшот.

## Решение

Append-only таблица `ops` (`board_id, seq, actor, counter, lamport, kind, delta, received_at`) с уникальным индексом `(board_id, actor, counter)` — вставка идемпотентна по повтору (V1, `docs/spec/protocol.md`). Периодически — таблица `snapshots` (`board_id, upto_seq, state`) с результатом `compact(replay(ops до upto_seq))`. При подключении клиент получает снапшот + хвост журнала после него (I5, § 6 `consistency-model.md`).

## Рассмотренные варианты

- **Журнал + снапшоты в PostgreSQL (выбран)** — реляционная БД уже нужна проекту (участники, доски, метаданные), не нужен отдельный движок специально под event log. Уникальный индекс даёт идемпотентность бесплатно средствами БД (`ON CONFLICT DO NOTHING`), без ручной дедупликации в коде.
- **Хранить только текущее CRDT-состояние целиком (без журнала операций)** — проще для чтения, но каждое переподключение требует пересылки полного состояния доски целиком, а не только пропущенных операций; на доске с сотнями стикеров это заметный трафик и нарушает лимит размера сообщения (`protocol.md` § 1).
- **Отдельный движок очереди/лога (Kafka, Redis Streams)** — оправдан при многих серверных инстансах и высокой нагрузке; для одного процесса на доску (ограничение, явно принятое в `docs/brief.md` § Что НЕ делаем — «горизонтальное масштабирование») это инфраструктурная сложность без выгоды.

## Последствия

- Компактизация обязана быть доказанно безопасной операцией (I4, ADR-0003), иначе снапшот может незаметно разойтись с полным replay журнала.
- Один процесс сервера на доску (`BoardHub` в памяти, § Архитектура `CLAUDE.md`) — журнал в Postgres не спасает от гонки между несколькими процессами, обрабатывающими одну доску одновременно; если это понадобится, потребуется отдельный ADR (например, распределённая блокировка по `board_id` или `LISTEN/NOTIFY`, уже упомянутый в `CLAUDE.md` как возможное будущее расширение).
