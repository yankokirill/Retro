# ADR-0001: Использовать монорепо на npm workspaces и TypeScript везде

- **Статус:** принято
- **Дата:** 2026-09-13

## Контекст

Проект состоит минимум из трёх взаимозависимых частей: ядро CRDT, сервер (WebSocket + REST + журнал операций) и клиент. Ядро CRDT должно работать одинаково в браузере и на сервере — если реализация конкурентности различается между клиентом и сервером, свойства, доказанные для одной, ничего не говорят о другой. Отдельная задача курса — единая проверка `npm run check` одной командой на чистой машине проверяющего.

## Решение

Один репозиторий, npm workspaces (`apps/*`, `packages/*`), TypeScript во всех пакетах. Сервер — Node 24 + Fastify. Клиент — React + Vite. Хранилище — PostgreSQL 17 + Drizzle ORM. Форматирование и линт — Biome, тесты — Vitest + fast-check.

## Рассмотренные варианты

- **Монорепо, TypeScript везде (выбран)** — одна реализация `packages/crdt`, общие типы протокола (`packages/protocol`) проверяются компилятором на обеих сторонах, а не документацией, которая может разойтись с кодом.
- **Отдельные репозитории для клиента/сервера** — исключает случайное расхождение версий пакета `@retro/crdt`, но требует публикации и версионирования внутреннего пакета ради проекта, у которого один автор и один релизный цикл; лишняя церемония.
- **Разные языки на клиенте и сервере** (например, Python на сервере) — потребовал бы либо повторной реализации CRDT на двух языках (риск незаметного расхождения семантики), либо сериализации состояния через границу языков на каждую операцию.
- **pnpm/Turborepo вместо npm workspaces** — быстрее на большом монорепо, но независимому проверяющему из задания курса важно запустить проект без установки дополнительных инструментов; npm есть везде, где есть Node.

## Последствия

- Все версии зависимостей — в одном дереве `node_modules`; конфликт версий между пакетами придётся решать раньше, чем в отдельных репозиториях.
- `tsc -b` с project references (`tsconfig.json` в каждом пакете) — обязательное условие для того, чтобы типы `packages/crdt` и `packages/protocol` реально проверялись при сборке сервера и клиента, а не только внутри своего пакета.
- Открытым остаётся вопрос будущего масштабирования репозитория при появлении дополнительных сервисов — не актуален для объёма курсового проекта.
